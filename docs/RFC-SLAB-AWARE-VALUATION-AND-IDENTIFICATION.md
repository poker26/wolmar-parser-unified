# RFC: учёт слабов при парсинге, оценке и добавлении монеты по фото

Статус: согласован для реализации  
Дата: 28 августа 2026  
Проекты: `work/wolmar-identify-production`, `work/numismatics-identify-fix`

## 1. Решение

Слаб учитывается в трёх продуктовых потоках:

1. При первоначальном парсинге аукционных лотов.
2. При расчёте прогнозной цены во всех местах продукта.
3. При фотографировании монеты для добавления в «Мою коллекцию».

Дополнительно необходимы два технических потока:

4. Обратное заполнение сведений о слабах для уже сохранённых аукционных лотов.
5. Ручное исправление сведений о слабе в карточке коллекции.

Слаб относится к конкретному экземпляру или аукционному проходу. Он не является свойством `coin_type`.

```text
Парсеры ценовых источников ─────┐
                               ├──→ структурированные признаки слаба
Фото и ручной ввод коллекции ──┘
                                           │
                                           ▼
                              единый алгоритм оценки
                                           │
                         ┌─────────────────┴─────────────────┐
                         ▼                                   ▼
              прогноз аукционного лота          оценка «Моей коллекции»
```

## 2. Что есть сейчас

### 2.1. Парсинг Wolmar

Рабочая цепочка парсинга:

```text
Temporal parser activities
  → WolmarCategoryParser
  → WolmarParser5
  → auction_lots
```

`WolmarParser5` сохраняет фразу вида `В слабе NGC` внутри `coin_description`, но отдельно извлекает только `condition`. Компания слаба не хранится структурированно.

### 2.2. Расчёт цены

Единого алгоритма сейчас нет.

- `ImprovedPredictionsGenerator` используется для прогнозов аукционных лотов и в легаси-потоках коллекции.
- `temporal/collection-valuation-activities.js` отдельно рассчитывает оценку новой «Моей коллекции» по `type_id + grade`.
- В репозитории также находятся старые реализации `final-price-predictor`, `simplified-price-predictor` и `robust-predictions-generator`; перед изменением продакшена необходимо проверить, вызываются ли они фактически.

Обе основные реализации смешивают слабированные и неслабированные экземпляры одного грейда. Компания слаба не участвует в подборе аналогов.

### 2.3. Определение по фото

Сервис `numismatics-identify-fix/refserver.py` определяет тип монеты, но не извлекает наличие слаба, компанию и грейд с этикетки.

Промежуточный API `app-v1/identification/service.js` и Android-модели также не содержат этих полей.

## 3. Общая модель признаков

Во всех потоках используется одна семантика:

```json
{
  "slabStatus": "slabbed | raw | unknown",
  "gradingCompanyCode": "NGC | PCGS | NNR | RNGA | NRG | NGS | OTHER | null",
  "gradingCompanyRaw": "исходное написание или null",
  "gradeCode": "MS65 | PF69 | XF | null",
  "gradeSource": "slab_label | auction_house | user | unknown"
}
```

Правила:

- `slabbed` — наличие слаба явно установлено.
- `raw` — отсутствие слаба подтверждено пользователем или однозначно видно на полном фото/указано источником.
- `unknown` — данных недостаточно.
- Отсутствие слов о слабе в старом аукционном описании означает `unknown`, а не `raw`.
- Компания хранится каноническим кодом; исходное написание сохраняется для аудита.
- Неизвестная компания не блокирует сохранение `slabbed`.
- `gradeSource = slab_label` допустим только тогда, когда грейд прочитан с существующей этикетки.
- Поле `condition` аукционного лота нельзя автоматически считать грейдом слаба.

Нормализация алиасов выполняется одной общей функцией. Например, после проверки на данных `ННР`, `HHP` и `NNR` могут быть сопоставлены одному каноническому коду, а `РНГА` и `RNGA` — другому.

## 4. Поток 1: первоначальный парсинг аукциона

### 4.1. Нужно ли менять парсер

Да.

Не требуется переписывать загрузку страниц Wolmar. После извлечения `coinDescription` и `condition` парсер должен вызывать общую чистую функцию:

```js
extractSlabInfo({
  description: lotData.coinDescription,
  condition: lotData.condition,
  sourceFields: lotData.sourceFields
})
```

Результат сохраняется вместе с лотом.

### 4.2. Что извлекает парсер

- явное наличие слаба;
- исходное написание компании;
- канонический код компании;
- грейд только тогда, когда текст явно связывает его с этикеткой слаба;
- источник грейда;
- версию правил извлечения.

Положительные примеры:

- `В слабе NGC`;
- `В слабе ННР MS65`;
- `PCGS MS64, cert...`, если контекст однозначно относится к держателю.

Неоднозначные случаи:

- одиночное `NGC` без контекста;
- `condition = MS65`, но в описании нет связи с этикеткой;
- описание не упоминает упаковку.

В таких случаях нельзя выдумывать `slab_label`. Сохраняется `auction_house` или `unknown`.

### 4.3. Какие источники менять

Общий извлекатель должен применяться не только к новым лотам Wolmar, но ко всем источникам, продажи которых используются единым алгоритмом оценки.

Если в аналоги входят `numismat.ru`, Meshok или другие источники, их будущий импорт обязан заполнять те же поля. Иначе сопоставимость будет зависеть от источника данных.

## 5. Технический поток: исторические аукционные лоты

Изменение парсера не исправит ранее сохранённые записи. Нужен отдельный backfill всех `auction_lots`.

Backfill должен использовать ту же `extractSlabInfo`, что и новый парсер.

Порядок:

1. Dry-run без записи данных.
2. Частотный отчёт по фрагментам `В слабе ...` и найденным компаниям.
3. Проверка алиасов на ручной выборке.
4. Запись пакетами с версией извлекателя.
5. Повторный отчёт по покрытию и неизвестным компаниям.

Backfill не должен:

- менять исходное `coin_description`;
- превращать отсутствие упоминания в `raw`;
- перезаписывать ручные исправления;
- считать `condition` грейдом этикетки без текстового доказательства.

Минимальный отчёт:

- число лотов по источникам;
- число явных слабов;
- распределение компаний и алиасов;
- число слабов с читаемым грейдом;
- число сопоставимых продаж в разрезе `type + grade + slab status + company`;
- частые неизвестные написания;
- результаты ручной проверки точности.

## 6. Хранение данных

### 6.1. Аукционные лоты

Добавить к `auction_lots` либо в связанную таблицу один-к-одному следующие поля:

- `slab_status`;
- `grading_company_code`;
- `grading_company_raw`;
- `slab_grade_code`;
- `grade_source`;
- `slab_extractor_version`;
- короткий фрагмент исходного описания, послуживший основанием.

Конкретный способ — колонки или отдельная таблица — выбирается после проверки размера и схемы продакшен-БД. Семантика полей должна оставаться одинаковой.

### 6.2. Экземпляр «Моей коллекции»

В `collection_item` добавить:

- `slab_status` с исходным значением `unknown` для существующих записей;
- `grading_company_code`;
- `grading_company_raw`;
- `grade_source`.

Существующие `grade_system` и `grade_code` сохраняются.

Смена статуса на `raw` или `unknown` должна очищать компанию. Изменение статуса, компании или грейда запускает пересчёт оценки.

### 6.3. Снимок оценки

Каждый снимок оценки должен сохранять:

- `slab_status` оцениваемого экземпляра;
- компанию;
- грейд и его источник;
- уровень основания оценки;
- точные и расширенные аналоги отдельно;
- версию алгоритма;
- идентификаторы использованных продаж.

Это необходимо, чтобы историческая оценка оставалась воспроизводимой после изменения карточки или алгоритма.

## 7. Поток 2: единый расчёт прогнозной цены

### 7.1. Требование централизации

Правила подбора аналогов и расчёта цены должны находиться в одном доменном модуле.

Целевой интерфейс:

```js
valuateCoin({
  typeId,
  identityFallback,
  gradeCode,
  gradeSource,
  slabStatus,
  gradingCompanyCode,
  valuationDate,
  currency
})
```

Результат:

```json
{
  "low": 85000,
  "median": 105000,
  "high": 135000,
  "confidence": "medium",
  "basisLevel": "same_slab_group",
  "exactComparableCount": 1,
  "expandedComparableCount": 12,
  "methodVersion": "slab-aware-v1"
}
```

Адаптеры:

- аукционный лот преобразуется во вход `valuateCoin`;
- экземпляр «Моей коллекции» преобразуется в тот же вход;
- экрану, которому нужна одна прогнозная цена, передаётся `median`;
- экрану коллекции передаётся диапазон `low–high` и `median`;
- избранное, аналитика и другие потребители читают сохранённый результат, а не считают цену самостоятельно.

### 7.2. Сопоставимость продаж

Приоритет аналогов:

1. Тот же тип, грейд, статус слаба и та же компания.
2. Тот же тип, грейд и статус слаба с обоснованной статистической поправкой компании.
3. Тот же тип, грейд и статус слаба без надёжной поправки — более широкий диапазон и низкая уверенность.
4. Если грейд неизвестен — широкий диапазон релевантных продаж типа без присвоения выдуманного грейда.
5. Если статус слаба неизвестен — широкий диапазон рынка типа с низкой уверенностью, без предположения `raw`.

Нехватка продаж той же компании не должна автоматически оставлять пользователя без оценки. При допустимом расширении возвращается более широкий ориентир с пониженной уверенностью.

Ручные коэффициенты компаний запрещены. Поправка разрешена только при наличии воспроизводимого расчёта по завершённым продажам и результатов backtest.

### 7.3. Только текущее состояние

Алгоритм оценивает монету в том состоянии, в котором она находится сейчас.

Не рассчитываются и не отображаются:

- потенциальная цена после слабирования;
- потенциальный будущий грейд;
- выгода слабирования или переслабирования;
- рекомендация отправить монету в определённую компанию.

### 7.4. Устранение дублирующихся алгоритмов

Перед переключением необходимо составить карту фактических вызовов:

- `ImprovedPredictionsGenerator`;
- `collection-valuation-activities.js`;
- `collection-price-service.js`;
- `catalog/api.js`;
- `final-price-predictor.js`;
- `simplified-price-predictor.js`;
- `robust-predictions-generator.js`.

После внедрения:

- один модуль владеет подбором аналогов и вычислением диапазона;
- старые точки либо вызывают его через адаптер, либо удаляются из активной конфигурации;
- параллельное существование разных правил оценки запрещено;
- переключение выполняется через теневой расчёт и сравнение результатов.

## 8. Поток 3: фото для добавления в «Мою коллекцию»

### 8.1. Ответ распознавания

Определение типа монеты и наблюдение о слабе возвращаются раздельно:

```json
{
  "recognizedName": "5 рублей 1898 года",
  "catalogMatch": "ambiguous",
  "extracted": {
    "country": "Russia",
    "year": 1898,
    "denominationValue": "5",
    "denominationUnit": "rouble"
  },
  "slab": {
    "status": "slabbed",
    "gradingCompanyCode": "NNR",
    "gradingCompanyRaw": "ННР",
    "labelGradeCode": "MS65",
    "confidence": 0.96
  },
  "candidates": []
}
```

### 8.2. Правила распознавания

Модуль должен:

- определить наличие уже существующего слаба;
- прочитать компанию;
- прочитать грейд только с этикетки;
- вернуть `unknown`, если упаковка обрезана или неразличима;
- вернуть `null` для нечитаемых символов вместо догадки;
- позволить пользователю исправить результат до сохранения.

Модуль не должен:

- определять числовой грейд неслабированной монеты по фото;
- предполагать отсутствие царапин, дефектов гурта, чистки или других невидимых повреждений;
- прогнозировать результат будущего грейдинга;
- оценивать выгоду слабирования;
- объявлять слаб или монету подлинными по фотографии.

Компания слаба не участвует в выборе `coin_type`. Текст этикетки может служить дополнительным свидетельством года, номинала и разновидности, но итоговый тип всё равно проходит через существующий каталог и матчер.

### 8.3. Передача в приложение

Обновить:

- промпт и ответ `numismatics-identify-fix/refserver.py`;
- нормализацию `app-v1/identification/service.js`;
- API-контракт;
- Android-модели;
- черновик добавления монеты;
- сохранение `collection_item`.

После подтверждения карточки новые признаки передаются в `valuateCoin`.

## 9. Технический поток: ручное редактирование

Поля статуса слаба, компании и грейда должны быть доступны при ручном добавлении и редактировании карточки.

Это необходимо, когда:

- монета добавлена без фото;
- этикетка не читается;
- OCR ошибся в компании или грейде;
- пользователь заменил фотографии;
- фактическое состояние экземпляра изменилось.

Интерфейс не должен добавлять советы о слабировании. Достаточно редактируемых полей и текущей оценки после сохранения.

## 10. Порядок реализации

1. Проверить фактические точки расчёта цены и активные процессы в продакшене.
2. Утвердить общую структуру `SlabInfo` и нормализатор компаний.
3. Добавить поля хранения без изменения текущего расчёта.
4. Реализовать `extractSlabInfo` и тесты.
5. Подключить функцию к парсеру Wolmar и другим ценовым источникам.
6. Выполнить dry-run backfill и проверить алиасы.
7. Выполнить проверенный backfill.
8. Реализовать единый `valuateCoin` в теневом режиме.
9. Перевести аукционные прогнозы и «Мою коллекцию» на общий модуль.
10. Расширить фотоидентификацию, API и Android.
11. Добавить ручное исправление полей.
12. После backtest переключить основной расчёт и отключить дублирующие активные алгоритмы.

## 11. Критерии приёмки

1. Новый лот Wolmar с явным слабом сохраняет статус и компанию структурированно.
2. Тот же извлекатель применяется ко всем источникам, участвующим в оценке.
3. Исторические лоты обработаны backfill без изменения исходных описаний.
4. Отсутствие упоминания о слабе не считается доказательством `raw`.
5. `condition` не считается грейдом этикетки без доказательства.
6. Все продуктовые места используют один модуль подбора аналогов и оценки.
7. NGC, российский слаб и неслабированный экземпляр не смешиваются как точные аналоги.
8. При недостатке точных проходов система возвращает более широкий текущий ориентир, если существует рыночная база.
9. Фотоидентификация возвращает статус слаба, компанию и читаемый грейд этикетки.
10. Неслабированная монета не получает числовой грейд по фотографии.
11. Пользователь может исправить сведения о слабе перед сохранением и позднее в карточке.
12. Изменение статуса, компании или грейда запускает пересчёт.
13. В API и интерфейсе отсутствуют потенциальная цена после слабирования и рекомендации по слабированию.
14. Результаты parser-аудита, backfill и backtest сохранены отдельными артефактами.

## 12. Явные запреты для агента-исполнителя

Агент не должен:

- добавлять фотогрейдинг неслабированных монет;
- рассчитывать будущую цену после слабирования;
- давать советы о слабировании или переслабировании;
- создавать независимый расчёт цены для отдельного экрана;
- задавать премии компаний вручную;
- считать отсутствие слова `слаб` признаком неслабированной монеты;
- изменять `coin_type` ради хранения свойств физического экземпляра.
